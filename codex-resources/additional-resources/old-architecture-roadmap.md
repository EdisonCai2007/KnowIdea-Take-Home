# Architecture Roadmap

Status: Planning only
Date: June 5, 2026

## Summary

This roadmap locks the current architecture direction for the Decision Prover before implementation starts.

Overall rating: `8.8/10`

Core decision:
- Keep the external system shape as two stages:
  - `Stage 1`: interview and formalize
  - `Stage 2`: verify
- Implement Stage 1 internally as:
  - `planner -> formalizer -> critic`
- Keep Stage 2 deterministic:
  - code owns the verdict
  - code owns the derivation
  - code owns refutation
  - code owns UNDECIDABLE threshold logic

## Why This Direction Is Strong

- It matches the assignment's scoring priorities: honest formalization and sound verification.
- It reduces the biggest Stage 1 failure mode: inventing missing premises.
- It keeps the proof auditable because the derivation is generated by checks, not by model narration.
- It makes conservative reasoning natural: the system can say `UNDECIDABLE` when the facts do not force a conclusion.

## Rating

### Overall

`8.8/10`

### What pushes it up

- Strong separation between language interpretation and truth-checking.
- Good alignment with the battery and rubric.
- Clear path to an audit-first UI.
- Refutation and threshold logic are treated as real product requirements, not extras.

### What keeps it below a 9+

- The critic has some unavoidable semantic complexity.
- Approximate-value handling introduces extra logic in both formalization and verification.
- Open-ended variable handling makes Stage 1 planning less predictable than a narrow template system.

## Pros

- Deterministic verification is easier to defend in the README and walkthrough.
- The planner/gap-agenda layer keeps the interview disciplined without forcing proposals into a closed taxonomy.
- The critic catches a different class of failure than the verifier: invented or weakly grounded premises.
- The system can support both full pipeline runs and verifier-only runs on already-structured objects.
- The architecture is well suited to a plain audit UI because every artifact is inspectable.

## Cons

- More moving parts than a simple "LLM then verifier" design.
- A dynamic planner needs strong grounding rules or it can drift into vague questioning.
- Hybrid critic design needs careful rules to avoid over-blocking or missing drift.
- Range-based reasoning for approximate inputs adds complexity to the verifier.
- Less flashy than a multi-agent demo, even if it is more robust.

## Finalized Decisions

### 1. Public System Structure

- Keep the public product framed as two stages because that matches the assignment.
- Internally split Stage 1 into three components:
  - `planner`
  - `formalizer`
  - `critic`
- Keep Stage 2 as a dedicated verifier/refuter with no decision authority delegated to an LLM.

### 2. Stage 1 Planner

- Keep the strict structure at the output boundary only, aligned to `decision_battery.json`.
- Use a dynamic gap agenda rather than a rigid action-type checklist or finite planner taxonomy.
- Let the planner infer whatever variables, claims, assumptions, and constraints are needed for the specific proposal.
- Require every clarification question to name the check it unlocks, such as runway, feasibility, LTV/CAC, margin hurdle, or dominance.
- Keep the planner open to proposal-specific constraints and mixed-pattern decisions instead of forcing them into named templates.

### 3. Stage 1 Gap Agenda

- Use a generic internal planning artifact with items like:
  - `category`
  - `variable_or_claim`
  - `why_needed`
  - `blocking_check`
  - `current_grounding`
  - `status`
- Keep categories generic:
  - `action`
  - `objective`
  - `fact`
  - `constraint`
  - `assumption`
  - `unknown`
- Treat the agenda as a proof-oriented list of missing information, not as an ontology of business decision types.

### 4. Stage 1 Formalizer

- Formalize only what is grounded in the user proposal or the interview answers.
- Do not invent missing facts.
- If load-bearing information is missing, ask for it.
- Allow new fact keys and parameters when they are grounded and useful for verification.
- If the proposal still cannot be safely formalized after clarification, stop and surface the incompleteness rather than forcing a schema object.

### 5. Approximate Value Policy

- If the user gives an approximate value like "around 80k" and the value is load-bearing, Stage 1 must ask for:
  - an exact number, or
  - an explicit range
- If the user refuses to pin it down, store it as a range and let Stage 2 test both sides.
- Do not collapse approximate values into a single point estimate by default.

### 6. Formal Output Boundary

- The final Stage 1 output must still match the structured shape expected by the verifier and the battery.
- Facts should remain an open typed key-value map rather than a closed list of allowed fields.
- The planner may discover new variables dynamically, but the formalizer must normalize them into the fixed output schema before verification.

### 7. Critic Design

- Use a hybrid critic.
- Code-level critic checks should block verification when:
  - numeric facts have no grounding
  - boolean facts have no grounding
  - action parameters have no grounding
  - a hard constraint appears in the formal object without support
- Model-assisted critic checks should be limited to:
  - semantic drift
  - unit phrasing mismatches
  - wording inconsistencies
- Model-assisted findings become blocking only if they would change the math or constraint outcome.

### 8. Verifier Design

- Stage 2 must be deterministic.
- Use a strict precedence order in code:
  1. hard constraints
  2. dominance or alternative checks
  3. objective satisfaction
- Short-circuit on the first decisive failure.
- Build the derivation as an append-only list of typed steps while verification runs.
- Do not reconstruct the derivation after the fact.

### 9. Refutation Design

- Implement three explicit refutation paths in code:
  1. hard-constraint breakage
  2. explicit-baseline dominance
  3. algebraic flip-threshold solving for undecidable cases
- Treat refutation as required output, not optional commentary.

### 10. UNDECIDABLE Output Contract

- `UNDECIDABLE` must be a first-class return type.
- It must always include:
  - `pivotal_assumption`
  - `flip_threshold`
  - `supported_if`
  - `refuted_if`
- The verifier should not be able to return `UNDECIDABLE` without this payload.

### 11. Explanation Layer

- Keep Stage 2 explanations deterministic in v1.
- Generate summaries from the checked derivation using templates.
- Do not allow an LLM to add new proof steps, alter the verdict, or reinterpret the checked result.

### 12. UI Scope

- Keep the UI plain and audit-first.
- Required views for v1:
  - interview transcript
  - gap agenda or missing-information trace
  - formal object
  - critic findings
  - derivation steps
  - binding constraints
  - load-bearing assumptions
  - refutation output
- Do not commit to the assumption-toggle stretch goal in v1.
- Expose a verifier entry point that can re-run on an already-formalized object so the stretch goal remains feasible later.

## Risks To Watch

- The dynamic planner could become too loose if questions are not tied to explicit verifier needs.
- The gap agenda could become noisy if it tracks non-load-bearing unknowns.
- The critic could become noisy if it flags harmless phrasing differences.
- Interval reasoning for approximate inputs could spread complexity into many verifier rules.
- Dominance checks could become vague unless they are limited to explicit, available baselines.

## Build Order

1. Define the verifier types and return contracts first.
2. Build the verifier against `decision_battery.json` before any Stage 1 implementation.
3. Add tests for:
   - runway and reserve constraints
   - LTV/CAC checks
   - capacity and backlog checks
   - marketing caps
   - margin hurdles
   - dominance checks
   - UNDECIDABLE thresholds
4. Define the fixed formal output contract and the internal gap-agenda representation.
5. Build the Stage 1 planner to generate proof-oriented clarification questions from verifier needs, not action templates.
6. Build the formalizer to normalize dynamic variables into the battery-aligned schema.
7. Implement the critic in two passes:
   - code grounding pass
   - model-assisted semantic drift pass
8. Build the UI last against real verifier output.

## Success Criteria

- The verifier returns defensible results on the battery with sound derivations.
- Stage 1 asks for missing load-bearing facts instead of inventing them.
- The critic visibly catches unsupported formalization choices.
- A skeptical user can inspect the UI and trace the verdict to the exact assumptions, constraints, and derivation steps that caused it.
